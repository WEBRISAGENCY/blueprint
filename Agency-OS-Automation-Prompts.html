Automating your Pipeline & CRM with Claude

Two ready-to-use Claude automations that keep your Agency OS pipeline current on their own: one turns booked sales calls into pipeline leads, the other attaches call recordings and AI-written notes to the right lead. Copy a prompt, fill in a few values, and tell Claude to run it on a schedule.

What you'll set up

1
Pipeline Auto-Sync — every booked discovery/sales call on your scheduler becomes a lead in your pipeline's first column, deduped by email so it never doubles up. Runs twice a day.
2
Call Recording Sync — new Zoom / Google Meet recordings are matched to the right lead, and Claude writes a structured recap from the transcript and attaches the recording + notes to that lead's card. Runs twice a day.

Both run unattended on a schedule and are safe to re-run — the dedupe rules mean an overlap never creates duplicates.

Before you start — connect these & grab 5 values

In Claude, connect the tools each automation needs (Settings → Connectors), then collect the values below. You'll paste them into the prompts wherever you see an ORANGE PLACEHOLDER.

1 · Pipeline Auto-Sync scheduler → pipeline

Turns new bookings on your scheduler into pipeline leads. Paste this into Claude, replace the placeholders, then say: "Run this every day at 7am and 4pm."

Pipeline Auto-Sync — prompt
You are running my agency's "Pipeline Auto-Sync." Each run, pull new bookings from my scheduler and turn them into pipeline leads in my Agency OS database. This prompt is self-contained; you have no memory of prior runs.

CONNECTORS
- Scheduler: use the connected Calendly MCP (tools named ...users-get_current_user, ...meetings-list_events, ...meetings-list_event_invitees). Load them via ToolSearch if not already available.
- Database: use the connected Supabase MCP (execute_sql) against my Agency OS project, project_id = {{DB_PROJECT_ID}}. Load it via ToolSearch if needed. All writes target public.leads with account_id = '{{ACCOUNT_ID}}'.

STEP 1 — Ground in the scheduler
Call users-get_current_user; keep resource.uri.

STEP 2 — Find recent bookings (self-healing window)
Call meetings-list_events with user = that uri, status = 'active', count = 100, sort = 'start_time:asc', and min_start_time = (now minus 30 days in UTC, format 2026-01-02T03:04:05.000000Z). If pagination.next_page_token is present, keep paging until all events are retrieved. From the returned events, KEEP ONLY:
  (a) events whose "name" is exactly one of my sales-call event types: {{DISCOVERY_EVENT_TYPES}} (ignore all other event types, e.g. "30 Minute Meeting"), AND
  (b) events whose "created_at" is within the last 14 days.
Why this window: a healthy daily run only needs ~1 day of look-back, but a 14-day created_at window (over a 30-day start_time pull) means any run that is skipped, delayed, or fails is automatically caught up on the next run instead of dropping bookings permanently. Because Step 4 dedupes by email, re-seeing an already-synced booking is safe and never creates a duplicate — err on the side of a wider window.
If none qualify, write a one-line summary saying "No new bookings" and stop.

STEP 3 — Get invitee detail for each kept event
For each kept event, call meetings-list_event_invitees with uri = the event uri. Read the (active) invitee: name, email, timezone, questions_and_answers (array of {question, answer}), and tracking (utm_source/medium/campaign). Also keep the event start_time and event name.

Build these mapped fields per invitee:
- contact_name = invitee name (or "Unknown")
- email = invitee email (lowercased for matching)
- phone = answer to the question containing "Phone"
- website = answer to the question containing "Website"/"URL", normalized to https:// (strip http/https/www and any path). If not a real domain (e.g. "none", "N/A", a sentence), set website = null.
- company_name = the website domain if present, else the contact_name
- budget_range = answer to the question about monthly spend/budget if present
- custom_fields (jsonb) = {
    "source": "Calendly",
    "event_type": ,
    "booking_datetime": ,
    "qualification": ,
    "utm": ,
    "last_synced": 
  }
- notes = a short readable summary of the Q&A (one line per question: "Q — A")
Do NOT set expected_deal_value (leave it null; I fill it manually). Do NOT set status (let it take the table default so the lead lands in the first pipeline column, exactly like a manually-created lead).

STEP 4 — Upsert into public.leads (dedupe by email, never duplicate)
For each invitee, first check for an existing lead:
  SELECT id, custom_fields FROM public.leads
  WHERE account_id = '{{ACCOUNT_ID}}' AND lower(email) = '' LIMIT 1;
- If a row exists: UPDATE it — merge the new custom_fields into the existing (custom_fields || new_extra), and fill phone/website/budget_range/company_name only if the existing value is null/empty. DO NOT change its status or stage. Count it as "updated".
- If no row exists: INSERT a new lead with account_id, company_name, contact_name, email, phone, website, source='Calendly', budget_range, custom_fields (omit status so the DB default applies). Count it as "added".
Escape single quotes in all string values (double them), or use Postgres dollar-quoting ($tag$...$tag$). Use one execute_sql per lead; if one fails, continue and note it. Because the Step 2 window is intentionally wide, most rows on a normal run will already exist and should be skipped/updated — that is expected, not an error.

STEP 5 — Summary
Post a short summary of this run:
- "Added N new leads: "
- "Updated M existing leads: "
- "Skipped K already-in-pipeline"
- Any errors.
Keep it to a few lines.

Then tell Claude: "Schedule this to run every day at 7:00am and 4:00pm."

2 · Call Recording Sync recordings → lead notes

Finds new call recordings, matches them to the right lead, writes a structured recap from the transcript, and attaches the recording link + notes to that lead's card. Paste, replace placeholders, then say: "Run this every day at 9pm and 7am."

Call Recording Sync — prompt
You are running my agency's "Call Recording Sync." Each run, find new Zoom and Google Meet recordings of calls with prospects and attach them to the matching ACTIVE lead in my Agency OS pipeline. Self-contained; no memory of prior runs.

Run this TWICE DAILY: a late-evening main pass (catches same-day calls after Zoom finishes processing them) and an early-morning backstop that sweeps up anything still processing overnight. Both runs are identical — the dedupe rules in STEP 4 make the overlap harmless.

CONNECTORS (load via ToolSearch if not already available)
- Zoom: the connected Zoom MCP — recordings_list, get_meeting_assets.
- Google Drive: the connected Drive MCP — search_files.
- Database: Supabase MCP execute_sql, project_id = {{DB_PROJECT_ID}}, table public.leads, account_id = '{{ACCOUNT_ID}}'.

IMPORTANT — where the app reads recorded calls from:
Agency OS renders a lead's recorded calls from **metadata.calls** (a jsonb array on public.leads). Each call object MUST use exactly these keys (the shape the app's own "Add call" form writes):
{ "url": , "date": "YYYY-MM-DD", "title": , "source": "zoom"|"google meet", "summary":  }
Do NOT write to custom_fields — the app ignores it and the call will not appear on the card.

STEP 1 — Load active leads
Active statuses are the ones still in play (NOT not-qualified, deal-lost, or spam). Use my active set:
SELECT id, trim(contact_name) AS name, lower(trim(email)) AS email, status,
jsonb_array_length(COALESCE(metadata->'calls','[]'::jsonb)) AS n_calls, metadata->>'last_contact' AS last_contact
FROM public.leads
WHERE account_id='{{ACCOUNT_ID}}'
AND status IN ({{ACTIVE_STATUSES}});
Do NOT select the whole metadata column for every lead — it blows the token limit. Select only the scalar fields above.
NOTE — statuses are stored in lowercase_snake form. If you see an unfamiliar status, run a `GROUP BY status` first to re-derive the active set rather than assuming.
NOTE — contact_name values sometimes have leading/trailing whitespace or differ in case. Match with trim()+lower() (or a LIKE fallback) so you don't miss a lead.
NOTE — a lead's status is NOT evidence about whether a call happened. Only recordings_list and Drive tell you that.

STEP 2 — Zoom recordings (last 3 days)
Call recordings_list with from = (today minus 3 days, yyyy-mm-dd) and to = today, page_size 100 (page through if needed). Use UTC dates. For each meeting:
- Parse the topic, formatted "{{RECORDING_TITLE_FORMAT}}" (e.g. "David Klain: Discovery Call"). Take the prospect name out of it. If the topic has no name/event shape (e.g. "Team Working Session"), it's an internal meeting — skip it.
- Match that name (case-insensitive, trimmed) to an active lead's contact_name.
- Skip any meeting whose recording_files are all still status "processing" — no transcript yet. Report it as pending so the next run picks it up.
- ALWAYS PULL THE TRANSCRIPT AND WRITE NOTES. Call get_meeting_assets(meetingId = the meeting uuid, DOUBLE-URL-encoded: replace '=' with %253D, '/' with %252F, '+' with %252B).
- get_meeting_assets output routinely exceeds the token limit and gets saved to a file on the host filesystem that bash CANNOT reach. Use the Read tool, or delegate to a subagent via the Agent tool so the large blob stays out of your main context; ask it to return the recap plus the play_url and a transcript sanity-check.
- TRANSCRIPT LOCATION: the transcript lives at `recording.transcripts[0].timeline[]`, each item having `ts`, `end_ts`, `display_name`, `text`. Do NOT look for `.meeting_transcript.transcript_items[]`. There is often no summary/participants field — the raw transcript is the source of truth.
- Write a substantive, factual recap in the "summary" field using these all-caps sections with prose under each, blank line between: ATTENDEES / CURRENT SITUATION / WHAT THEY WANT / RECOMMENDATION / PRICING-TERMS / NEXT STEPS. Quote specific numbers and names verbatim. Write ONLY from what was actually said — do NOT invent. If a section has nothing, write "Not discussed."
- Build the call object:
  { "url": , "date": , "title": , "source": "zoom", "summary":  }
- URL CAVEAT: get_meeting_assets returns a different play_url than recordings_list, and Zoom rotates share URLs. Always store the recordings_list share_url so it stays consistent run to run.

STEP 3 — Google Meet recordings (last 3 days)
search_files with query: title contains 'Recording' and mimeType = 'video/mp4' and modifiedTime > 'T00:00:00Z'. Meet recordings are titled like " - YYYY/MM/DD HH:MM TZ - Recording". Ignore edited/marketing clips. Parse attendee names and match to an active lead. For notes, find the matching Meet transcript/Gemini notes Doc in the same Drive folder and read it, then write the same kind of recap. If no transcript can be found, note briefly that the recording is attached for review. Build the call object with "source":"google meet", "url": the file viewUrl, "date": from the title, "title": a short label, "summary": the notes.
NOTE — if this search returns empty, sanity-check by running `title contains 'Recording'` with no date filter to tell a genuine empty from a broken connector.

STEP 4 — Attach to the lead (append to metadata.calls, never duplicate)
For each matched lead, read its current metadata.calls array (may be absent). Treat a call as ALREADY ATTACHED — and skip it — if EITHER:
  (a) its "url" already appears in the array, OR
  (b) an existing entry has the same "source" AND "date" AND "title".
Rule (b) matters because Zoom rotates share URLs. When (b) fires but the URL differs, skip the append and mention the URL drift in the summary.
For each genuinely new call, append it, then write:
UPDATE public.leads
SET metadata = COALESCE(metadata,'{}'::jsonb) || jsonb_build_object('calls', ),
    updated_at = now()
WHERE id = ;
Also bump last_contact WITHOUT regressing it — only if the newest attached recording date is more recent than the existing metadata.last_contact:
UPDATE public.leads
SET metadata = metadata || jsonb_build_object('last_contact', )
WHERE id = 
AND COALESCE(metadata->>'last_contact','0001-01-01') < ;
Do NOT change status. Escape single quotes (dollar-quoting like $notes$...$notes$ is easiest for multi-line notes). Never write to custom_fields.

STEP 5 — Verify + summary
After writing, re-SELECT jsonb_array_length(metadata->'calls') and the new entry's title/source/summary length for each updated lead to confirm the append landed. Then post a short summary: "Attached N recordings to M leads: ", plus any recordings that matched no active lead (so I can check), any still processing (next run gets them), and any errors. Be precise about what you verified vs. inferred.

Then tell Claude: "Schedule this to run every day at 9:00pm and 7:00am."

How Claude saves these so you can reuse them

When you tell Claude to "run this on a schedule," it saves the prompt as a scheduled task — a reusable instruction file that Claude re-runs automatically at the times you set. You don't paste it again; it just runs. You can manage them anytime by asking Claude in plain language:

  • See them: "List my scheduled tasks."
  • Change timing: "Change the Call Recording Sync to run at 10pm instead."
  • Run once now: "Run the Pipeline Auto-Sync now."
  • Pause / remove: "Turn off the Pipeline Auto-Sync." / "Delete it."
  • Edit the logic: "In my Call Recording Sync, also include the 'nurturing' status as active."

Keep this document as your master copy. If a task ever gets deleted or you're setting Claude up on a new machine, paste the prompt above again and re-schedule it — the placeholders are the only thing you need to refill.

Good to know: both automations are read-mostly and idempotent — safe to run as often as you like. Pipeline Auto-Sync dedupes by email; Call Recording Sync dedupes by URL and by source+date+title. Running twice a day (or re-running by hand) will never create duplicate leads or double-attach a recording.
